# Undo Log Handling for Secondary Indexes

This document explains how undo logs work for secondary indexes in OrioleDB, particularly in the context of transactions that modify data affecting secondary indexes.

## Overview

Secondary indexes in OrioleDB follow the same MVCC (Multi-Version Concurrency Control) principles as primary indexes, utilizing undo logs to maintain previous versions of tuples. This allows transactions to be rolled back and enables snapshot isolation for concurrent transactions.

## How Secondary Indexes Store Previous Versions

### DELETE + INSERT Strategy (Not In-Place Update)

Secondary indexes in OrioleDB handle modifications differently from primary indexes. Understanding this difference is crucial:

**Primary Indexes:**
- Use `BTreeOperationUpdate` for updates
- Modify tuples in-place and create undo records with the old tuple data
- The undo chain links versions at the same physical location

**Secondary Indexes:**
- Use `BTreeOperationDelete` + `BTreeOperationInsert` for updates
- Mark the old entry as deleted (creates undo record)
- Insert a new entry (may be at a different location if key changed)
- This is true even when only the indexed column changes

### When Undo Chains Are Created for Secondary Indexes

Undo chains in secondary indexes are created during **DELETE operations**, not UPDATE operations:

1. **When you update an indexed column**: 
   - The old secondary index entry is marked as deleted → **creates undo record**
   - A new entry is inserted at a new location → **creates new tuple with undo pointer**
   - You see: old entry marked deleted, new entry at different offset

2. **When you update a primary key**:
   - Same behavior: old secondary index entry deleted, new one inserted
   - The primary key is part of the secondary index key, so it's essentially a key change

3. **When you delete a row from the table**:
   - Secondary index entry is marked as deleted → **creates undo record**
   - The undo record stores the previous state for rollback

### Why This Approach?

This DELETE + INSERT strategy for secondary indexes:
- Simplifies the implementation (no complex in-place updates)
- Works well since secondary indexes don't store the full tuple data
- Allows the new entry to be at a different location if the key changed
- Still supports full rollback through the undo chain on the deleted entry

### Undo Chain Structure

### Example: What You Actually See

Consider a transaction that updates indexed columns:

```sql
CREATE TABLE vegetables (
  id int PRIMARY KEY,
  name text,
  count int
) USING orioledb;

CREATE INDEX vegetables_count_idx ON vegetables(count);

INSERT INTO vegetables VALUES (1, 'Tomato', 10);
UPDATE vegetables SET count = 15 WHERE id = 1;
```

**What happens in the secondary index `vegetables_count_idx`:**

1. **Initial INSERT**: Entry `(count=10, id=1)` is inserted
2. **UPDATE operation** internally performs:
   - **DELETE**: Entry `(count=10, id=1)` is marked as deleted
     - Creates an undo record with the previous tuple header
     - The deleted entry remains on the page with `deleted` flag
   - **INSERT**: Entry `(count=15, id=1)` is inserted at a new location
     - May be at a different page offset
     - Has its own tuple header with undo pointer

**Visual representation:**
```
Before UPDATE:
Page offset 1: (count=10, id=1) [active]

After UPDATE (before commit):
Page offset 1: (count=10, id=1) [DELETED, has undo chain]
Page offset 2: (count=15, id=1) [active, new entry]
```

### Transaction Semantics

**Until Commit:**
- The old entry `(count=10, id=1)` cannot be physically removed
- It remains marked as deleted with an undo chain
- Other transactions with earlier snapshots can see the old version
- If the transaction rolls back, the delete is reverted

**After Commit:**
- The deleted entry becomes invisible to new transactions
- The undo record is retained as long as needed for existing snapshots
- Eventually, the undo record is evicted and the deleted entry can be cleaned up

## Undo Log Structure for Secondary Indexes

### Implementation Details

All index types (primary, secondary, and TOAST) are initialized with the same undo log configuration in `index_btree_desc_init()`:

```c
// From src/tableam/tree.c
desc->undoType = UndoLogRegular;
```

This means all indexes:
- **DO** participate in the undo log system  
- **DO** create undo records for modifications
- **DO** maintain undo chains for version history
- **CAN** rollback changes using the undo log

However, the **type of operation** differs:

**Primary Indexes:**
```c
// From src/tableam/operations.c - o_tbl_indices_overwrite()
modify_result = o_btree_modify(&GET_PRIMARY(descr)->desc, 
                               BTreeOperationUpdate,  // ← UPDATE
                               newTup, BTreeKeyLeafTuple, ...);
```

**Secondary Indexes:**
```c
// From src/tableam/operations.c - o_update_secondary_index()
// DELETE old entry
o_btree_modify(&id->desc, BTreeOperationDelete, ...);  // ← DELETE
// INSERT new entry  
o_btree_modify(&id->desc, BTreeOperationInsert, ...);  // ← INSERT
```

The key insight: Secondary indexes use **two separate operations** (DELETE + INSERT) instead of a single UPDATE operation. The undo records are created during the DELETE operation.

### Tuple Header with Undo Pointer

Each tuple in a secondary index (leaf tuple) contains a `BTreeLeafTuphdr` header with:

- **xactInfo**: Transaction information (OXid - transaction ID, CommitSeqNo)
- **undoLocation**: Pointer to the previous version in the undo log
- **deleted**: Deletion status flag
- **lockMode**: Row lock mode (if any)

### Undo Record Types

Secondary indexes use the same undo record types as primary indexes:

- **ModifyUndoItemType**: Records modifications (insert/update/delete)
- **RowLockUndoItemType**: Records row locks
- **Page-level undo**: For compaction, splits, and merges

## Transaction Semantics

### Delete Operations

When a transaction deletes tuples from a table with secondary indexes:

```c
// From src/tableam/operations.c - o_update_secondary_index()
if (old_valid)
    res.success = o_btree_modify(&id->desc, BTreeOperationDelete,
                                 nullTup, BTreeKeyNone,
                                 (Pointer) &old_key, BTreeKeyBound,
                                 oxid, csn, RowLockUpdate,
                                 NULL, &callbackInfo) == OBTreeModifyResultDeleted;
```

This:
1. Marks the secondary index tuple as deleted
2. Creates an undo record via `make_undo_record()` with the previous state
3. Links it in the undo chain for potential rollback

### Update Operations (DELETE + INSERT)

When a transaction updates indexed columns:

```c
// From src/tableam/operations.c - o_update_secondary_index()
// Step 1: Delete the old entry
if (old_valid)
    o_btree_modify(&id->desc, BTreeOperationDelete, ...)

// Step 2: Insert the new entry  
if (new_valid)
    o_btree_modify(&id->desc, BTreeOperationInsert, ...)
```

**NOT** a single UPDATE operation like primary indexes! Each step:
- DELETE creates an undo record for the old entry
- INSERT creates a new entry (potentially at different location)

**Important:** Primary indexes use `BTreeOperationUpdate` for in-place modifications, while secondary indexes always use DELETE + INSERT.

### Rollback Behavior

If a transaction is aborted or rolled back, the system uses the `page_item_rollback()` function from `src/btree/undo.c` to:

1. Traverses the undo chain for affected tuples
2. Restores previous tuple headers and data
3. Reverts deletions by unmarking tuples (changing deleted flag back)
4. Removes inserted tuples that haven't been committed

For secondary indexes, this means:
- The DELETE is reverted (tuple no longer marked as deleted)
- The INSERT is removed (new entry is deleted from the page)
- The secondary index returns to its pre-transaction state

## Key Differences from PostgreSQL Heap Tables

### No Bloat in Main Storage

Unlike PostgreSQL's heap tables where deleted tuples cause bloat until VACUUM runs:

- **OrioleDB**: Old versions are stored in the undo log, not on the main data pages
- **Benefit**: The main B-tree structure remains compact
- **Space Reclamation**: Happens automatically as undo logs are evicted

### Row-Level Undo

OrioleDB uses row-level undo records that:
- Are more space-efficient than page-level MVCC
- Allow fine-grained rollback operations
- Support features like `ROLLBACK TO SAVEPOINT`

## WAL and Recovery Considerations

### Secondary Indexes Are Not WAL-Logged

Important distinction from primary indexes:

- **Primary Key Trees**: Are WAL-logged
- **TOAST Trees**: Are WAL-logged  
- **Secondary Indexes**: Are **NOT** WAL-logged

### Recovery Process

During recovery, secondary indexes are rebuilt from primary keys:

1. Primary key and TOAST trees are recovered from WAL
2. Secondary indexes are reconstructed by scanning primary keys
3. This ensures consistency without logging secondary index changes

### Checkpointing Order

Checkpoints are written in this order:
1. TOAST trees (first)
2. Primary key trees
3. Secondary indexes (last)

This ordering ensures that secondary indexes can always be rebuilt from checkpointed primary key data.

## Undo Log Lifecycle

### Retention Requirements

The undo log retains records to support:

1. **Rollback**: Active transactions that might abort
2. **Snapshots**: Concurrent transactions with earlier snapshots
3. **Recovery**: Transactions in progress during checkpointing

### Eviction

Undo records are evicted when:
- No active snapshots need them (tracked via `minProcRetainLocation`)
- Not needed for potential rollback
- Past the checkpoint retain location

### Storage

- **In-Memory**: Recent undo records in circular buffer (controlled by `orioledb.undo_buffers`)
- **On-Disk**: Older undo records evicted to disk files (`orioledb_undo/` directory)

## Concurrency and Visibility

### Snapshot Isolation

Transactions see consistent snapshots by:
1. Reading the current tuple version on the page
2. Following undo chains to find the version visible to their snapshot
3. Applying transaction visibility rules (based on OXid and CommitSeqNo)

### Lock-Free Reads

Secondary index reads don't require locks because:
- The page state mechanism allows lock-free reading
- Undo chains provide version history
- Change tracking detects concurrent modifications

## Summary

**Yes, secondary indexes in OrioleDB maintain previous versions** through the undo log system, but using a different strategy than primary indexes:

### Key Differences:

**Primary Indexes:**
- Use `BTreeOperationUpdate` for modifications
- Update tuples in-place
- Create undo records that chain versions at the same location

**Secondary Indexes:**
- Use `BTreeOperationDelete` + `BTreeOperationInsert` for updates
- Old entry marked deleted (creates undo record)
- New entry inserted (may be at different location)

### When Undo Chains Are Created:

- ✅ **DELETE operations** - Always create undo records
- ✅ **UPDATE operations** - Create undo record for the DELETE part
- ✅ **INSERT operations** - May reuse deleted slot, maintaining undo chain
- ❌ **No single UPDATE undo record** - Updates are split into DELETE + INSERT

### What You'll Observe:

When updating an indexed column, you see:
```
Page offset 1: (old_key, pk) [DELETED with undo chain]
Page offset 2: (new_key, pk) [ACTIVE new entry]
```

This design provides:
- ✅ Full transactional semantics with rollback support
- ✅ Snapshot isolation for concurrent readers  
- ✅ MVCC guarantees through undo log
- ✅ Simpler implementation for secondary indexes
- ✅ No bloat in the main B-tree structure
